# Phase 0 Research: AST + Symbol Intelligence

All decisions below are either directly inherited from `research/ARCHITECTURE_DECISION_GATE.md` (ratified, not re-litigated) or newly resolved against the **actual current implementation** of `specs/001-code-intelligence-foundation` (inspected directly in this pass, not assumed from its spec/plan prose).

## 1. WASM Tree-sitter execution mechanism

**Decision**: `web-tree-sitter` (the official WASM bindings for tree-sitter) + `tree-sitter-wasms` (prebuilt `.wasm` grammar binaries), loaded via Nitro's native Cloudflare Workers WASM-import support.

**Rationale**: `research/ARCHITECTURE_DECISION_GATE.md` §5 ("AST mechanism") already ratifies WASM tree-sitter over native Rust (impossible in Workers — JS/WASM only) and over hand-rolled parsers (reimplements what grammars already solve). `research/CODEGRAPH_RESEARCH.md` §2 evidences the exact package pair (`web-tree-sitter` + `tree-sitter-wasms`) as CodeGraph's own working WASM extraction backend — `ADOPTION_MATRIX.md` item 1 marks this ADAPT (reuse the tool choice, build our own extraction layer around it, not copy CodeGraph's ~6,000-line extraction module wholesale).

**New evidence found in this pass** (not previously verified): inspecting `vite.config.ts` and `node_modules/nitro/dist/_presets.mjs` directly (not assumed) confirms the project's `cloudflare-module` Nitro preset (the one this repo actually builds with — `vite.config.ts:20`, unchanged since Feature 001) already ships `wasm: { lazy: false, esmImport: true }` in its preset definition. This means a plain `import grammarModule from "tree-sitter-wasms/out/tree-sitter-java.wasm"` is bundled and instantiated as an ES module `WebAssembly.Module` by Nitro's own build pipeline — no manual `[[wasm_modules]]` binding in `wrangler.toml`, no custom Rollup/Vite WASM plugin, and no new Nitro configuration is required. This directly de-risks the "can a WASM grammar even load in this deployed Worker" question with a concrete, inspected fact rather than a general Cloudflare-docs claim.

**Alternatives considered**: A native Rust/WASM performance kernel (CodeGraph's own optional path) — eliminated outright, not merely deferred, because Workers cannot execute native code at all, and `ADOPTION_MATRIX.md` item 19 already flags this DEFER for the unconstrained case, let alone the Workers-execution path. Hand-written per-language parsers — rejected as reimplementing solved grammar logic for no evidenced benefit.

## 2. Initial language scope

**Decision**: Exactly Tier 1 from `research/ARCHITECTURE_DECISION_GATE.md` §5 — **Java, JavaScript, TypeScript, TSX** (TypeScript and TSX are two distinct `tree-sitter-typescript`-family grammars, both required to cover `.ts` and `.tsx` files respectively).

**Rationale**: Already ratified ("RATIFIED WITH CONSTRAINTS... ready to lock into the `sdd/03-ast-symbols` phase scope") against RepoAtlas's own cataloged-repository language distribution (45.7% combined share). Feature 002's spec (FR-002) already locks this in; this research confirms no new language-distribution query is needed — the prior analysis remains the authoritative evidence base.

**Alternatives considered**: Broader coverage matching Graphify/CodeGraph's 25/41-language scope — explicitly rejected by the ADR as reference-project scope, not RepoAtlas-evidenced scope, and rejected again here for the same reason (`sdd/03-ast-symbols/PHASE.md`'s own "Initial languages" line names exactly these four).

## 3. Grammar/runtime bundling strategy

**Decision**: Bundle only the four Tier 1 grammar `.wasm` files (`tree-sitter-java`, `tree-sitter-javascript`, `tree-sitter-typescript`, `tree-sitter-tsx`) plus `web-tree-sitter`'s own core runtime `.wasm` directly into the Worker via the ESM-import mechanism confirmed in §1. Tier 2/3 grammars are not bundled at all in this feature (not lazy-loaded from R2 either — that mechanism is explicitly deferred, since no Tier 2/3 support exists yet to motivate it).

**Rationale**: `research/ARCHITECTURE_DECISION_GATE.md` §5 flags the 64 MiB uncompressed Worker bundle-size limit as the concrete, evidence-based reason to keep the directly-bundled grammar set narrow — this reinforces, rather than conflicts with, the Tier-1-only language scope decided independently in §2.

**Open feasibility question carried to Risks (§6) below**: the *aggregate* size of `web-tree-sitter`'s core runtime WASM plus four grammar WASMs, added to the existing app's own bundle (React, Three.js, Radix, etc., already sizeable), has not been measured in this pass — this is a build-time fact that can only be confirmed by actually running `bun run build` with the dependency installed, which this planning phase does not do (no application code is added here).

## 4. Language detection

**Decision**: Deterministic, extension/filename-based mapping — no content sniffing, no heuristic/LLM classification. `.java` → Java; `.js`/`.jsx`/`.mjs`/`.cjs` → JavaScript; `.ts`/`.mts`/`.cts` → TypeScript; `.tsx` → TSX (its own grammar, not merely "TypeScript with JSX enabled" — `tree-sitter-typescript`'s package ships `typescript` and `tsx` as two separate grammars, confirmed by `CODEGRAPH_RESEARCH.md` §2's note that TS/TSX are "commonly extracted alongside" as related-but-distinct concerns).

**Rationale**: Directly required by spec FR-001 ("detect... sufficient to select a matching parsing grammar") and `sdd/03-ast-symbols/PHASE.md` requirement 1 ("deterministic parsers/AST extraction") — extension-based detection is itself deterministic (same input always produces the same language, no ambiguity), unlike shebang/content sniffing which can misclassify.

**Alternatives considered**: GitHub Linguist-style heuristic detection (content sampling, vendored-file exclusion) — rejected as unevidenced complexity for a Tier-1-only, extension-unambiguous scope; worth revisiting only if Tier 2/3 ever introduces genuinely ambiguous extensions.

## 5. Symbol extraction mechanism (AST → common intermediate representation)

**Decision**: Per-language tree-sitter query files (`.scm` query syntax, tree-sitter's own pattern-matching query language, not custom code per grammar) define capture patterns for each of the five symbol kinds (Module, Class, Interface, Function, Method) per language; a single, shared query-execution engine walks each grammar's query captures into one common `Symbol` intermediate representation (kind, name, range, parent).

**Rationale**: Directly matches `sdd/03-ast-symbols/PHASE.md` requirement 5 ("language-specific analyzers SHALL emit a common intermediate representation"). Tree-sitter's query mechanism is the standard, evidenced way both reference projects (and tree-sitter's own ecosystem, e.g. `tags.scm` conventions used for GitHub's own code navigation) express "which AST node shapes mean what" without hand-writing an AST-walking function per language — this keeps each language's specifics isolated to one declarative query file rather than duplicated imperative walker logic.

**Alternatives considered**: Hand-written imperative AST walkers per language (visit every node, switch on `node.type`) — CodeGraph's own approach in `src/extraction/tree-sitter.ts` (~6,000 lines) per `CODEGRAPH_RESEARCH.md` §2, but explicitly not adopted wholesale (`ADOPTION_MATRIX.md` item 1: ADAPT, not copy) — the query-based approach is simpler for exactly the narrower five-kind, Tier-1-only symbol model this feature needs, without needing CodeGraph's full 30+-language, framework-aware extraction surface.

## 6. Feasibility risks requiring a spike (explicitly flagged, not resolved here)

Per this task's explicit instruction, these are named as spike-required risks rather than papered over with an assumption:

1. **`web-tree-sitter`'s `Parser.init()` WASM-instantiation path under Workers — RESOLVED 2026-09-20, with a version-pin correction.** `web-tree-sitter@0.27.0` (the `bun add`-resolved latest at the time T001 ran) was tested first and **failed**: its `Language.load()`/`loadSync()` internally require a WASM custom section named `dylink.0` (Emscripten's current dynamic-linking metadata format), verified by direct inspection of `web-tree-sitter.js`'s `getDylinkMetadata()` (hard `failIf(name2 !== "dylink.0")`). The installed `tree-sitter-wasms@0.1.13` grammar binaries carry the **legacy** `dylink` custom section (confirmed via `WebAssembly.Module.customSections(mod, "dylink.0").length === 0` vs `customSections(mod, "dylink").length === 1`), which 0.27.0 rejects outright — a real parse attempt threw `need dylink section`. This is a binary-format version mismatch between the two npm packages, not a Workers-specific or architectural failure. **Resolution**: `web-tree-sitter@0.25.10` (same official `tree-sitter/tree-sitter` repo/maintainers, not deprecated, latest release before the `dylink`-fallback was dropped in 0.26.0) retains a `dylink.0`-then-legacy-`dylink` fallback (`getDylinkMetadata`'s two-attempt `customSections` lookup, confirmed by direct source inspection) and was verified end-to-end: `Parser.init({ instantiateWasm(imports, successCallback) { WebAssembly.instantiate(coreModule, imports).then(i => successCallback(i, coreModule)); return {}; } })` (zero `fetch()`/filesystem calls, confirmed Workers-compatible) followed by `Language.load(new Uint8Array(grammarBytes))` produced **real, correct, error-free ASTs for all four Tier 1 grammars** (Java: `class_declaration`/`super_interfaces`/`method_declaration`; JavaScript: `function_declaration`/`class_declaration`/`method_definition`; TypeScript: `interface_declaration`/`method_signature`; TSX: `function_declaration`/`jsx_element`), each with `tree.rootNode.hasError === false`. **Action taken**: `package.json`/`bun.lock` updated to pin `web-tree-sitter@0.25.10` (not `^0.27.0`/latest) — this pin is load-bearing, not cosmetic; a future `bun update` must not silently move past 0.26.0 without re-verifying this fallback. **New implementation-phase detail surfaced by this version** (deferred to T022, not resolved here — no extraction code written): 0.25.10's `Language.load()` takes only `string | Uint8Array` (no `loadSync(WebAssembly.Module)` — that method was added later, in the same 0.26.0 release that dropped the legacy-`dylink` fallback, so it isn't available on the version we need). Nitro's plain `.wasm` ESM import (no query suffix) auto-instantiates via `unwasm`'s exports-first codegen (not useful here); `?module`-suffixed imports (`unwasm`'s `id.endsWith("?module")` branch, confirmed by direct inspection of `node_modules/nitro/dist/_build/common.mjs`) yield a raw `WebAssembly.Module` — usable for the **core** runtime (fed to `instantiateWasm`, tested above) but not directly usable for **grammars**, since `Language.load()` needs raw bytes and a `WebAssembly.Module` cannot be reserialized back to bytes in JS. T022 will need a bytes-yielding source for grammar `.wasm` files in the deployed Worker — the Cloudflare `ASSETS` binding (`env.ASSETS.fetch()`, already configured in this repo's `wrangler.json`/`"assets"` block for static-asset serving, zero external network hop) is the leading candidate, to be confirmed when T022 is actually implemented, not before.

3. **Per-file CPU budget for a genuinely large single file — RESOLVED (with a methodology caveat) 2026-09-20.** Tested real parses (`web-tree-sitter@0.25.10` + `tree-sitter-wasms@0.1.13`, the pinned versions, via Bun 1.3.14 / V8) of synthetic-but-realistic Java/JavaScript/TypeScript/TSX fixtures at 10 KB, 100 KB, 500 KB, 1, 2, 5, 8, 12, and 20 MB, 5 repeats per size (first-run vs. steady-state separated to isolate one-time warmup from steady parsing cost).
   - **First attempt produced a real crash**: a `RuntimeError: Aborted()` inside the shared WASM runtime, first surfacing on TypeScript at ~5 MB, then (after the runtime was already poisoned) cascading to every other grammar. Root-caused by direct inspection of the test harness itself, not the parser: intermediate `Tree` objects from the 5-repeats loop were never explicitly `.delete()`'d, so each repeated parse accumulated additional WASM linear memory across the run rather than releasing it — a genuine memory-hygiene bug in the harness, not a per-file engine limit.
   - **Corrected methodology** (explicit `tree.delete()` after every single parse, not just the last one of each size): all four grammars parsed **cleanly and correctly** (`rootNode.hasError === false` at every size) up to **20 MB**, the largest size tested, with **no crash, no error, and no super-linear degradation at any point** — every size-doubling step showed a matching time-doubling step (`~LINEAR` at every transition, largest deviation a mild sub-linear blip on TSX's smallest 10→100 KB step, i.e. fixed per-parse overhead amortizing, not a risk).
   - **Steady-state throughput** (bytes of source per ms of parse time, plateauing after ~500 KB): JavaScript ≈8.6–9.2 KB/ms, TypeScript ≈8.2–8.5 KB/ms, TSX ≈7.9–8.1 KB/ms, Java ≈11.3–11.7 KB/ms (Java fastest per byte, TSX slowest — consistent with relative grammar complexity). At 20 MB, steady-state parse time was ≈2.3–2.5 s for JS/TS/TSX and ≈1.8 s for Java.
   - **Peak memory**: process RSS (Bun) grew smoothly and boundedly with the corrected methodology — reaching ≈1.06–1.32 GB by the end of the full 4-language × 9-size sweep (cumulative across the whole test run, not per-file), with no runaway growth once trees were freed per-iteration.
   - **Explicit limitation, stated per this task's instruction, not glossed over**: this is Bun/V8 wall-clock timing on local Apple Silicon hardware — **not** a Cloudflare Workers CPU-time measurement. Workers meters actual CPU time (not wall-clock) on a different JS/WASM engine (V8 isolates, same JS engine family as this test's runtime, but a different host environment with different scheduling, I/O-wait accounting, and isolate memory limits) via a documented but not directly reproducible-locally metering model. No Workers-specific number is claimed or should be inferred from these figures alone.
   - **Implementation-relevant conclusion**: the crash-vs-clean-parse contrast is itself the most actionable finding — **T029 (`extraction-pipeline.ts`) MUST call `tree.delete()` (or equivalent) immediately after a file's symbols are extracted, before moving to the next file in a batch**, not defer cleanup to garbage collection or batch-end. This is now a concrete implementation requirement surfaced by this spike, not a speculative concern. Given clean linear scaling with no crash through 20 MB (far beyond any realistic single source file — real-world files this large are essentially always generated/minified artifacts, not the median case), **no hard file-size ceiling is justified by the measurements themselves**; however, a generous defensive ceiling (e.g., ~10 MB, well past 99.9%+ of real source files) is still recommended as a circuit-breaker for the oversized-file fallback (spec User Story 3, `FR-017`), justified by the local-vs-Workers timing gap above and by Workers' shared per-invocation CPU budget (parsing is not the only cost in a unit — D1/R2 I/O and other files in the same batch also consume it), not because parsing itself was shown to fail. The exact threshold remains an implementation-phase tuning constant, per this document's own established "tunable, not hardcoded" posture (§ config.ts pattern).

None of these risks block writing this plan (they are runtime/measurement questions, not open design questions — the *mechanism* decided above does not change regardless of their outcome, only implementation-phase tuning constants and a possible fallback path do), consistent with how Feature 001's plan handled its own analogous "exact checkpoint threshold" open question.

4. **CRITICAL — the T012/T022 `instantiateWasm` mechanism does not actually work against a real deployed Cloudflare Worker (discovered 2026-09-21, T064 live validation).** T012's spike and T022's own tests validated the core-WASM-instantiation approach by feeding `Parser.init({ instantiateWasm })` a pre-compiled `WebAssembly.Module` obtained via `setTestCoreWasmModule` (a `bun test`-only injection hook, since Bun's `.wasm?module` resolver doesn't behave like Nitro's) — this **entirely bypasses `web-tree-sitter`'s own generated Emscripten glue's normal initialization path**. T022 itself disclosed this gap explicitly: *"`grammar-provider.ts` is not yet imported by any reachable route/server-fn... so `bun run build` does not itself bundle/exercise this file — the `?module` import mechanism is proven by T012's spike, not by this build."* That gap was closed for the first time by this session's T058/T059 (server-fn registration), and the first real production run (T064) immediately surfaced a real failure: every genuine Tier-1 source file, on the real deployed Worker, fails during parsing with `"Cannot read properties of undefined (reading 'href')"` — 100% reproducible across 2 independent live snapshots (10 real files). Read-only inspection of `.output/server/_libs/web-tree-sitter.mjs` (vendored Emscripten glue) shows it retains its own default `locateFile` fallback (`new URL("tree-sitter.wasm", import.meta.url).href`) that our custom `instantiateWasm` does not appear to fully suppress in the real bundled/deployed context — Cloudflare Workers has no global `location` object, a plausible source of the `undefined.href` read. **Not fixed** — this requires new diagnostic/implementation work on the approved T012/T022 mechanism itself (e.g., explicit `locateFile`, or a different Parser.init options shape), which needs explicit authorization before being attempted, per this session's operating rules. **Practical impact**: Feature 002's orchestration (queue, checkpointing, retry, D1 persistence, all 5 query functions) is fully verified live and correct; the tree-sitter parse step itself does not yet work in the real deployed environment, despite 129/129 local tests passing (all of which use the injection hooks that structurally cannot catch this).

**Update 2026-09-21, deployed fix + a second, deeper finding**: `ensureWorkerLocationPolyfill()` (backfills `self.location` before `Parser.init()`) was written, verified locally (tsc clean, 129/129 tests), and — with explicit user authorization — deployed to production. Re-running live validation against a fresh snapshot (`sindresorhus/is-obj`) confirms the `location.href` crash is **gone** — but every real Tier-1 file now fails with a **different, new** error: `"WebAssembly.instantiate(): Wasm code generation disallowed by embedder"`. This is a **known, documented Cloudflare Workers platform restriction**: Workers do not permit compiling/instantiating a `WebAssembly.Module` from a byte buffer obtained at runtime (e.g. via `fetch()`/an `ASSETS` binding read) — only WASM modules imported *statically at build time* (which the platform pre-compiles and binds ahead of the sandbox's runtime restrictions) are permitted to instantiate. This directly conflicts with T022's approved grammar-loading design: `grammar-provider.ts`'s `fetchGrammarBytes()` reads each grammar `.wasm` file's bytes from the `ASSETS` binding at runtime, then calls `Language.load(bytes)`, which internally does exactly the kind of dynamic runtime WASM compilation Workers blocks. The **core** runtime WASM (`tree-sitter.wasm`) does not hit this, because it's loaded via a genuine build-time `?module` static import (`coreWasmModule`, pre-compiled by Nitro/unwasm at build time) — only the four **grammar** WASMs, which needed a bytes-yielding runtime source per T022's own disclosed constraint ("`Language.load()` needs raw bytes, not a Module, at this web-tree-sitter version — no `loadSync(WebAssembly.Module)` available"), hit this wall. **Not fixed at the time** — see the 2026-09-21 investigation update immediately below for the resolved design.

**Investigation update, 2026-09-21 (research only, per explicit user instruction — no production code changed or deployed as part of this update)**:

Tested locally whether a viable, Workers-compatible fix exists without weakening any constraint (must stay WASM tree-sitter, no native binding, no runtime WASM compilation from fetched bytes, Tier-1 scope unchanged, Feature 001/003 untouched).

1. **`web-tree-sitter@0.26.x`/`0.27.0` upgrade — ruled out, empirically re-confirmed.** `npm view` shows `0.27.0` as latest; these versions dropped the legacy-`dylink` fallback (require `dylink.0`). `tree-sitter-wasms` is at its latest, `0.1.13`, and its grammar binaries carry only the legacy `dylink` section (re-confirmed, not just cited from the earlier T012 spike). No newer `tree-sitter-wasms` release exists with `dylink.0`-format grammars. Upgrading `web-tree-sitter` alone cannot load these grammars at all, at any version currently published — this path is dead regardless of the Module-vs-bytes question.
2. **Root-cause mechanism, precisely identified by reading `node_modules/web-tree-sitter`'s actual (non-vendored, non-minified) TypeScript/compiled source**: `Language.load(input)`'s public API only accepts `Uint8Array | string` — it always resolves to raw bytes and calls the internal `loadWebAssemblyModule(bytes, {loadAsync:true})`. But `loadWebAssemblyModule`'s own internal `loadModule()` function (in the Emscripten-generated glue, still present at this pinned version) **already contains a `WebAssembly.Module`-shortcut branch**: `if (binary instanceof WebAssembly.Module) { const instance = new WebAssembly.Instance(binary, info); return Promise.resolve(postInstantiation(binary, instance)); }` — i.e., the *low-level* grammar-linking mechanism already supports being handed a pre-compiled `Module` instead of bytes, skipping the disallowed dynamic-compile step entirely. Only the *public* `Language.load()` wrapper never exercises this branch, because it always passes bytes.
3. **Real local experiment (not theoretical)**: wrote a script that (a) pre-compiles each of the four Tier-1 grammar `.wasm` files into a `WebAssembly.Module` via `WebAssembly.compile()` — simulating exactly what a build-time `?module` static import produces — then (b) monkeypatches the global `WebAssembly.instantiate` for the duration of one `Language.load(bytes)` call, intercepting the *exact* byte buffer being loaded and substituting `WebAssembly.instantiate(precompiledModule, imports)` (the Module-form call, which Workers already allows — it's the same operation the core runtime's `instantiateWasm` already performs successfully in production) instead of the disallowed bytes-form call. Real parse, all four Tier-1 grammars, using the exact pinned `web-tree-sitter@0.25.10` + `tree-sitter-wasms@0.1.13`, no version change: **Java, JavaScript, TypeScript, TSX all produced correct, error-free ASTs** (`hasError: false`, correct `rootNode.type`). Test script and results were not committed (deleted after the run, per "do not implement" instruction).
4. **Confirmed Nitro build support for our own grammar files**: temporarily added a `?module` import of `public/wasm/tree-sitter-java.wasm` (mirroring the existing core-module import) into a local, uncommitted, reverted-after-test copy of `grammar-provider.ts`, referenced it so it wouldn't be tree-shaken, and ran a real `bun run build`. Result: Nitro/unwasm produced a genuine build-time-compiled chunk, `.output/server/wasm/tree-sitter-java-<hash>.wasm`, identical treatment to the already-proven-working core module's own `.output/server/wasm/tree-sitter-*.wasm` chunk. This confirms the `?module` mechanism is **not** special-cased to `node_modules` — it works generically for any `.wasm` file in the project, including our own `public/wasm/*.wasm` grammars. Build succeeded with zero errors; typecheck and the full local test suite were re-verified clean afterward, and the temporary edit was fully reverted (confirmed via `git diff` showing zero residual change) before this write-up.
5. **Bundle-size**: no material change expected — the four grammar `.wasm` files (≈5.8 MB total, already measured in risk 2) would move from "static asset fetched via `ASSETS` at runtime" to "build-time-compiled-and-embedded chunk," the same class of artifact the core module already is. Risk 2's 64 MiB cap headroom (~8%) is unaffected in any meaningful way by this reclassification.

## 7. Persistence approach

**Decision**: Extend the existing `data/code-intel-schema.sql` (the one shared schema file Feature 001 already established for all Code Intelligence D1 tables) with additive-only new tables; no new Cloudflare binding, no dedicated graph database, reusing Feature 001's exact `D1DatabaseLike` thin-query-layer pattern (`persistence/d1-client.ts`) and its `bun:sqlite`-backed test double (`tests/support/d1-sqlite-adapter.ts`) unchanged.

**Rationale**: `research/ARCHITECTURE_DECISION_GATE.md` §4 already ratifies D1+R2 with no dedicated graph database — that decision was for the eventual Engineering Graph too, so it applies here a fortiori for a strictly-simpler symbol table. Inspecting `data/code-intel-schema.sql` and `tests/support/d1-sqlite-adapter.ts` directly (not assumed) confirms both are additive-friendly: the schema file has no versioning/migration machinery to fight, and the SQLite test adapter already loads this exact file, so new tables are automatically available to tests with zero test-harness changes.

## 8. Queue model for a second Cloudflare Queue

**Decision**: A second Cloudflare Queue (`repo-atlas-symbol-extraction`, producer + consumer, declared in `wrangler.toml` alongside the existing `repo-atlas-snapshot-acquisition` queue) with its own Nitro plugin file, registered alongside (not replacing) `plugins/cloudflare-queue.ts` in `nitro.config.ts`'s `plugins` array.

**Rationale**: Inspecting `node_modules/nitro/dist/presets/cloudflare/runtime/_module-handler.mjs` directly (not assumed) shows the Worker's single `queue(batch, env, context)` export forwards Cloudflare's native `MessageBatch` object — which carries its own `.queue` name property — into one `cloudflare:queue` Nitro hook. Multiple hook listeners are supported (Nitro/hookable's standard multi-listener dispatch); each listener is responsible for checking `batch.queue` and ignoring batches meant for the other queue. This is a direct, low-risk extension of Feature 001's exact established pattern (`plugins/cloudflare-queue.ts`) — no change to that existing file, no new Nitro capability required beyond what's already proven live (Feature 001's live smoke test on 2026-09-20 confirmed the `cloudflare:queue` hook actually fires in the deployed Worker, not just in theory).

**Verified directly against the installed dependency** (2026-09-20, `/speckit-analyze` remediation pass — this claim was previously asserted from general library knowledge, not inspected): `node_modules/hookable/package.json` reports version `6.1.1`. `node_modules/hookable/dist/index.mjs` — `hook(name, fn)` (lines 96–97 and 202–203) does `this._hooks[name] = this._hooks[name] || []; this._hooks[name].push(fn)`, i.e. `_hooks[name]` is an array every registered listener is pushed onto, never overwritten. `callHook`/`callHookWith` (lines 151–164, 219–222) pass `[...this._hooks[name]]` (or `this._hooks[name]`) into `callHooks`/`caller`, which recursively invokes every entry in that array in sequence (lines 31–40) with no early-exit/short-circuit mechanism exposed to a listener. **Confirmed**: two `hook("cloudflare:queue", ...)` registrations (Feature 001's existing listener plus this feature's new one) both fire for every batch, regardless of which queue it came from — each listener's own `batch.queue` filter is what makes this safe, exactly as this decision already assumed. No conflict found; the queue architecture above is unchanged by this verification.

**Alternatives considered**: Reusing the single existing `SNAPSHOT_QUEUE` for both acquisition and extraction messages (tagging message bodies with a `type` discriminator instead of using two queues) — rejected because it would mix two independently-scaling, independently-retryable workloads onto one queue's shared `max_batch_size`/`max_retries` configuration, and because Feature 001's `snapshot-worker.ts` is explicitly "the only writer of `snapshots.status`" (plan.md Queue/Job Boundaries) — a second concern sharing its queue risks blurring that single-writer invariant. A second, independent queue keeps the two feature's failure/retry/backpressure characteristics fully decoupled, matching this feature's own FR-026 ("this feature is additive, read-only with respect to Feature 001's data").

## 9. `createServerFn` trigger surface — closing Feature 001's observed gap

**Decision**: Every server function this feature exposes (`extractSnapshotSymbols`, `getExtractionStatus`, `listSymbols`, `getSymbol`, `getFileExtraction`) is registered in the client module graph (via `useServerFn`, mirroring `feature-001-server-fn-registration.tsx`'s mechanism), not only the trigger + status pair.

**Rationale**: Feature 001's own live-validation pass (`PROGRESS.md`, 2026-09-20 entry) directly discovered that `Feature001ServerFnRegistration` registered only `acquireSnapshot`/`getSnapshotStatus`, leaving `listSnapshotFiles`/`getSnapshotFile`/`getRepositoryHistory` unreachable over the deployed `/_serverFn/<id>` HTTP surface — verification of those had to fall back to direct D1/R2 inspection. Feature 002's own User Story 5 (Queryable symbol retrieval) exists specifically so a later feature (or an operator) can query symbols without re-running extraction; leaving `listSymbols`/`getSymbol` HTTP-unreachable would silently reproduce the exact gap just discovered and documented one feature ago. This is a directly-evidenced correction, not a speculative improvement.

## 10. Extractor/grammar version provenance

**Decision**: A single application-level constant, `SYMBOL_EXTRACTOR_VERSION` (analogous in spirit to Feature 001's `codeIntelConfig()` tunables module, `src/lib/code-intel/config.ts`), incremented manually whenever a query file, grammar version, or extraction-logic change would alter extraction output for previously-processed files. Every `file_extractions` and `symbols` row records the extractor version that produced it (FR-014).

**Rationale**: Matches `research/ARCHITECTURE_DECISION_GATE.md` §7's required evidence metadata field `analyzer_version` ("so re-indexing after an extractor bugfix is distinguishable from a real source change") — this feature is the first to actually need that field, since Feature 001 has no analogous "did the acquisition logic itself change" concern (acquisition is provider-content-driven, not analyzer-logic-driven).
