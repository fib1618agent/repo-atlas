## 1. Cloudflare Plan Constraint (resolves the blocking NEEDS CLARIFICATION raised during planning)

**Decision needed**: What per-invocation CPU budget must relationship-extraction units target?

**Finding**: Confirmed directly against the live account (2026-09-21, dashboard screenshot + official Cloudflare pricing doc supplied by the user) — this account's Workers subscription is **Workers Free**, not Paid. Only `R2` shows as a separate "R2 Paid" line; `Workers` shows "Workers Free — Active" with no Workers Paid subscription. This settles the ambiguity `research/ARCHITECTURE_DECISION_GATE.md` §3 (written pre-deployment) left open ("a paid plan should be assumed as a deployment prerequisite" — that assumption was never actually verified against the real account until now, and turns out to be wrong).

**Hard limit, confirmed via the account's own pricing reference**: Workers Free = **10 ms CPU time, max per invocation** (not per-request only — this is the account-wide per-invocation ceiling, which applies to queue-consumer invocations too, not just HTTP). There is no published Free-tier exception for queue consumers; the only documented Free/Paid split for queue consumer *wall-clock duration* is 15 min on both tiers, but CPU time is capped at 10 ms on Free regardless of trigger type. **[AMENDED 2026-09-24 17:09 +04:00 — Cloudflare documentation review: the Free Queue Consumer CPU limit is NOT confirmed; X = CONTRADICTORY, Y = PARTIAL, T007 STOPPED; see research.md Amendments A4.]**

**Reconciling with Feature 002's live success**: T068 already ran real tree-sitter WASM parsing (Java/JS/TS/TSX, single files, not large batches per parse) inside a queue-consumer invocation on this same Free-tier account and succeeded, with zero `failed` extractions. Cloudflare's own docs note isolates have "built-in flexibility to allow for cases where your Worker infrequently runs over the configured limit" and are only terminated if they "consistently" exceed it — Feature 002's per-file parse (one small/medium source file, immediate `tree.delete()`, no batching of the parse step itself within one file) evidently stays within or close enough to that flexibility margin. This is empirical evidence bounding what a *single* parse of *one* file costs, not a guarantee that added work per invocation is free.

**Decision**: Feature 004 MUST target the same per-invocation shape empirically proven safe by Feature 002 — **one file re-parsed per unit, nothing larger** — and must NOT add speculative additional CPU-heavy work (e.g., a second full-snapshot scan, an O(n²) all-pairs candidate search) inside that same invocation. Where a relationship type's resolution needs more than a cheap, indexed D1 lookup against already-persisted Feature 002 data, it is deferred rather than force-fit into the 10 ms budget (see §2, Deterministic Resolution Scope).

**Alternatives considered**:
- **A. Assume Paid, plan for 5-minute CPU budget** — rejected outright now that the actual plan is confirmed Free; would produce a plan the account cannot execute.
- **B. Batch multiple files per relationship-extraction unit (mirroring Feature 002's 50-file `CODE_INTEL_EXTRACTION_BATCH_SIZE`)** — rejected. Feature 002's batch config governs how many files one *queue message* claims responsibility for across potentially multiple internal loop iterations; T068's live success was demonstrated per-file parse cost, not per-50-file-batch parse cost within one invocation. Reusing that batch size for a *heavier* workload (parse + resolve, vs. parse + insert) without new evidence would be a new, unverified assumption on the same class of platform limit that already produced one production incident (T064's `ASSETS.fetch()` WASM-compilation failure) from an untested assumption. Not repeating that mistake.
- **C. One file per unit, cheap indexed-lookup resolution only in the same invocation (chosen)** — smallest unit of work that reuses a shape already proven live on this exact account and plan tier.

**Confidence**: High for the plan-tier fact itself (directly observed, not inferred). Medium for the exact CPU-ms Feature 002's per-file parse actually consumes (never measured/logged) — flagged as an explicit Phase-2 (tasks) prerequisite: instrument and log observed CPU time per relationship-extraction unit during implementation, so the one-file-per-unit assumption can be confirmed or tightened further with real numbers, not just precedent.

## 2. Deterministic Resolution Scope Under the CPU Budget

**Decision**: Within one file's relationship-extraction invocation, only *indexed, bounded* D1 lookups are permitted for resolution — e.g., "look up a symbol by `(snapshot_id, kind, name)`" (a single indexed query), not "scan every symbol in the snapshot and rank candidates." This directly shapes which evidence states are reachable without exceeding budget:

- `IMPORTS`/`EXTENDS`/`IMPLEMENTS`: resolvable in one indexed lookup per reference (import path → `file_extractions` by path; class/interface name → `symbols` by `(snapshot_id, kind, name)`) — cheap, in scope for `RESOLVED`.
- `CALLS`/`USES`/`REFERENCES`: resolvable only when the callee/reference name has exactly one candidate under the same cheap indexed lookup; more than one candidate is recorded `AMBIGUOUS` with the candidate set from that same bounded lookup (not a wider search) — no additional type-inference or scope-resolution pass is attempted, consistent with FR-007's "must not fabricate a single target."
- `EXPORTS`: derived directly from the file's own already-extracted top-level symbols' `is_exported` flag (Feature 002 data, zero new parsing needed beyond what the relationship-bearing parse pass also visits) — cheapest of the eight. **[AMENDED 2026-09-24 16:46 +04:00 — R4 decision C: EXPORTS is parse-derived within Feature 004, no longer a D1-only derivation from `symbols.is_exported`; see Amendments A2]**

**Rationale**: This keeps every unit's added CPU cost bounded to "one extra parse pass + a handful of indexed point-lookups," which is the smallest increment on top of Feature 002's already-proven-safe per-file parse cost — not a new unbounded search space.

**Canonical evidence representation (2026-09-22 clarification, closes `/speckit-analyze` finding H2)**: `relationships.evidence_state` is **one single-valued column**, exactly one of `EXTRACTED`/`RESOLVED`/`INFERRED`/`AMBIGUOUS`/`UNKNOWN` per row — never a compound "extraction happened + separate resolution outcome" pair. An external/unresolvable import is `evidence_state = 'UNKNOWN'` on its one relationship row, full stop (not `'EXTRACTED'` with some second, separate "target-resolution state" field — no such field exists in data-model.md's schema). `EXTRACTED` is reserved for structural facts whose evidence *is* the observation itself, with no resolution step attempted (`CONTAINS` and `EXPORTS`, both pure-D1 §4 derivations that never reach the resolver at all). Every fact the resolver *does* attempt to resolve (`IMPORTS`/`EXTENDS`/`IMPLEMENTS`/`CALLS`/`USES`/`REFERENCES`) lands on exactly one of `RESOLVED`/`AMBIGUOUS`/`UNKNOWN` per this section's rules — never `INFERRED` (this v1 resolver has no confidence-scored heuristic path, per spec.md's Assumptions; `INFERRED` remains a valid vocabulary member for a future, out-of-scope resolver, not a state this version ever emits).

**Alternatives considered**: A full symbol-table/scope-resolution pass (real type-aware call resolution) — rejected for v1 as both out of evidenced CPU budget and out of the ratified §6 core scope (no `Package`/framework-resolver work is in scope per the spec's Assumptions).

## 3. Reuse vs. New Extraction Path (resolves spec FR-001's "no second AST extraction path" against the practical need to inspect import/call/inheritance syntax)

**Finding**: Feature 002's `extractFile` (`extraction-pipeline.ts`) discards its parsed tree immediately after building symbols (`tree.delete()`, explicitly to avoid the WASM-runtime memory issue T014 found) — there is no cached AST to reuse. Deriving `IMPORTS`/`CALLS`/`EXTENDS`/`IMPLEMENTS`/`USES`/`REFERENCES` requires inspecting syntax (import declarations, call expressions, `extends`/`implements` clauses) that Feature 002's own `symbols` table does not capture (it only records declaration sites, not usage sites).

**Decision**: Feature 004 re-parses each file exactly once per relationship-extraction unit, reusing Feature 002's own `getParser`/`grammar-provider.ts` **unchanged** (same WASM grammars, same build-time `?module` + scoped `WebAssembly.instantiate` mechanism T066 already validated live) — new relationship-focused `.scm` query files per language (mirroring `symbols/queries/*.scm`'s existing pattern), not a new grammar-loading or language-detection mechanism. This satisfies FR-001's actual intent (no *second, independent* extraction pipeline/grammar system) while being honest that a second *parse pass* is structurally unavoidable given Feature 002 keeps no AST around to reuse. `CONTAINS`, by contrast, needs no parse at all (§4).

**Alternatives considered**: Cache/serialize Feature 002's parsed tree for Feature 004 to reuse — rejected; would require Feature 002 to change its own memory-management behavior (which T014 specifically fixed to prevent a WASM runtime abort) to serve a future feature, violating this feature's own FR-017 (no Feature 002 modification) and constitution Principle V (minimal scope, no speculative infra).

## 4. CONTAINS Needs No Parse — Separate, Cheaper Unit Type

**Decision**: `CONTAINS` relationships (directory→subdirectory, directory→file, class/interface→method) are derivable entirely from already-persisted Feature 002 columns (`directories.parent_path`, `file_extractions.directory_path`, `symbols.parent_symbol_id`) via plain D1 reads — no R2 read, no parse, no WASM. This is materially cheaper than the parse-dependent relationship types, so it runs as its own `unit_type = 'contains'` job phase (bounded batches of directories/symbols, sized generously since there's no parse cost), separate from `unit_type = 'parsed'` (one file per unit, §1). Running `CONTAINS` first, as its own cheap phase, also means a snapshot gets *some* useful relationship data even if the parse-dependent phase is still in progress or partially fails.

**Alternatives considered**: Deriving `CONTAINS` inline during the per-file parsed phase — rejected; would tie a near-free operation to the tightest-budget unit type for no benefit, and would recompute `CONTAINS` once per file instead of once per directory/symbol.

## 5. Queue Topology

**Decision**: One new Cloudflare Queue, `repo-atlas-relationship-extraction`, with its own `RELATIONSHIP_QUEUE` binding and its own `cloudflare:queue` Nitro hook listener (`plugins/cloudflare-relationship-queue.ts`), filtering on `batch.queue`, coexisting with (not replacing) Feature 001's `SNAPSHOT_QUEUE` and Feature 002's `SYMBOL_QUEUE` — direct structural repeat of Feature 002's own precedent for adding `SYMBOL_QUEUE` alongside `SNAPSHOT_QUEUE` (research.md §8 in Feature 002, and `plugins/cloudflare-symbol-queue.ts`).

**Free-plan Queues budget check**: Free plan includes 10,000 Queue operations/day (confirmed from the user's pricing reference). A "operation" is a read/write/delete against a queue. With one-file-per-unit granularity, a snapshot of N Tier-1 files produces on the order of N enqueue + N consume operations for the parsed phase, plus a small constant number for the `contains` phase — comfortably within 10,000/day for the snapshot sizes already exercised in Feature 002's live validation (33 files). Flagged as a documented cap, not a blocking risk: **a snapshot whose Tier-1 file count alone would approach several thousand files in one relationship-extraction run could approach the daily Queues operation cap** — out of scope to solve here (no evidenced need yet), noted in Risks.

**Alternatives considered**: Reusing `SYMBOL_QUEUE` with a distinct message shape — rejected; would couple two features' queue consumers to one topic's `max_batch_size`/`max_retries` tuning, and Feature 002's consumer would need to learn to ignore relationship messages (or vice versa), which is exactly the coupling Feature 002 itself avoided by introducing a second queue instead of reusing `SNAPSHOT_QUEUE`.

## 6. Storage

**Decision**: D1 only, additive to `data/code-intel-schema.sql` (the same shared schema file Feature 001 and Feature 002 both already extend) — no new database, no dedicated graph database, no new R2 usage (relationship extraction reads existing Feature 001 R2 bytes via the existing `getObject`, writes zero new R2 objects). Matches `research/ARCHITECTURE_DECISION_GATE.md` §4's ratified "D1, no dedicated graph store" decision, carried forward unchanged from Feature 002.

**Free-plan D1 budget check**: 5 GB storage, 5,000,000 row reads/day, 100,000 row writes/day, all free. Relationship rows are small (fixed-width columns, no blob data); at Feature 002's already-demonstrated live scale (33 files, 77 symbols), even a generous multiplier (each file producing tens of relationship rows) stays orders of magnitude under the daily write cap. Flagged as a Risk to revisit only if/when snapshot scale grows far beyond what's been exercised so far — not a blocking constraint today.
