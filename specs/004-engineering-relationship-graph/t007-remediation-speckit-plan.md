### D2 — PAUSED job lifecycle state (resolves SYM-04 and the K.1 PAUSED ambiguity)

**Decision**: PAUSED is introduced as an **explicit eighth job-lifecycle state**, not a wording amendment to guarantee 7. Guarantee 7 ("repository lifecycle states are projections over these job states… with no extra bookkeeping store") is **not weakened or reinterpreted** — instead, the *job* model itself grows a state so the *projection* remains bookkeeping-free once PAUSED exists as a real state. Full semantics (drafted here for the eventual contract-amendment text at RT-05; **not applied to `contracts/local-job-engine.md` in this pass**):

| Aspect | Specified semantics |
|---|---|
| **Meaning** | A job that would otherwise be claimable (PENDING) or is already claimed/running (CLAIMED/RUNNING) for a snapshot that has been paused by the owner; no new claims occur while paused. |
| **Valid transitions INTO PAUSED** | PENDING → PAUSED (an unclaimed job, on pause). CLAIMED → PAUSED is **not** valid — a job already claimed continues to RUNNING and either finishes normally or is later reclaimed on lease expiry; pause does not interrupt in-flight work (matches the already-observed F-5 behavior: "RUNNING units finish or checkpoint"). RUNNING → PAUSED is likewise **not** valid, for the same reason. |
| **Valid transitions OUT of PAUSED** | PAUSED → PENDING on `resume()` (the snapshot's pause flag is cleared and the job becomes claimable again). PAUSED → nothing else — a paused job cannot be claimed, retried, or reclaimed directly; it must first return to PENDING. |
| **Interaction with cancel()** | `cancel()` on a snapshot with PAUSED jobs moves those PAUSED jobs to FAILED('cancelled') exactly as it currently does for PENDING/RETRYING jobs (today's `jobs.ts:247-256` logic extends to include the PAUSED state in its `WHERE state IN (...)` clause). |
| **Interaction with cancelHalt()** | Unaffected — `cancelHalt` only sets a control-table flag that stops new claims; it does not rewrite job rows regardless of state, so PAUSED jobs are untouched by it, same as any other state today. |
| **Interaction with leases** | A PAUSED job holds no lease (it was never claimed, or its claim was released on the PENDING→PAUSED-adjacent transition — see below). **Clarification needed at RT-05**: since CLAIMED/RUNNING → PAUSED is invalid (row above), only PENDING jobs actually become PAUSED; a job that was CLAIMED/RUNNING at pause time keeps running under its existing lease, unaffected by PAUSED. |
| **Interaction with retries/reclaims** | RETRYING jobs (backoff-pending) are **not** moved to PAUSED by this decision — a RETRYING job due for retry stays RETRYING/PENDING-on-schedule; pause prevents new *claims*, which already prevents a RETRYING job from being reclaimed as PENDING while paused (the existing `claim()` code path already checks the pause flag before doing any claim work, per `jobs.ts:120-131`, so this is consistent with existing behavior, not a new mechanism). |
| **Terminal vs. non-terminal** | **Non-terminal.** PAUSED always leads back to PENDING (resume) or to FAILED (cancel) — it is never a final resting state for a job the way COMPLETED/FAILED/SKIPPED/CANCELLED are. |
| **Persistence requirements** | PAUSED must be a value in the job row's `state` column (durable, survives process restart) — **not** a separate flag table lookup the way `t7_control.paused` works today. This is the specific point on which this decision departs from the current harness implementation: today's `pause()`/`resume()` (`jobs.ts:236-245`) write to `t7_control`, a snapshot-level flag, and no job row's state changes. Under this decision, pausing a snapshot must additionally transition its eligible (PENDING) job rows to PAUSED, and resuming must transition them back to PENDING — this is a real implementation task (RT-05/RT-10-adjacent), not merely a documentation change, contrary to how it was classified as "documentation-only" in Phase 4's change-type table below. **Phase 4's table is corrected by this addendum**: PAUSED is now a harness-implementation item, not documentation-only. |

### D3 — RT-09 / persistence batching axis and preserved semantics

**Decision**: the primary batching axis is **bounded row count** (accumulate relationship+candidate rows across files until a row-count bound is reached, then commit), with **bounded file count and bounded elapsed time as additional safety limits** (whichever bound is hit first triggers a commit) — not a single-axis design. The exact numeric bounds are an implementation-time tuning question (informed by, but not fixed to, M-L3's curve: e.g. M-L3's 1000-row batches already showed most of the throughput benefit with much less latency variance than "all rows in one commit"), not decided by this addendum.

**CRITICAL, non-negotiable per the owner's decision**: the first remediation implementation MUST preserve, unchanged:
- **File-level completion atomicity** — each file's job row still transitions to COMPLETED only together with that file's own relationship rows becoming durable; a crash before a batch's commit must leave **every file whose rows are in that uncommitted batch** as if none of them had run (not partially-COMPLETED), which in practice means the completion write for a file cannot be observably "ahead of" its own data — it may lag behind the batch commit but never precede it.
- **File-level containment** — a single file's fault (F-2's scenario) must still result in only that file's unit reaching FAILED/RETRYING, with every other file — including other files already accumulated in the same in-flight batch — still reaching COMPLETED normally once the batch (minus the faulted file's rows) commits. This likely requires the faulted file's rows to be excluded from the batch's commit (e.g., a per-file savepoint inside the batch transaction that can be rolled back independently) rather than failing the whole batch.
- **Failure/retry semantics, idempotency, and durability expectations** — unchanged from today's per-unit guarantees; PERSIST-02/PERSIST-03 (already specified in Phase 3) state this precisely and are not altered by this addendum, only reinforced as non-negotiable rather than merely preferred.

**Explicit stop condition, as directed**: if a row-batched design that also preserves per-file completion atomicity AND per-file containment cannot be built against the existing contract as written, the implementer MUST STOP and raise a specification amendment (to `contracts/local-job-engine.md`'s guarantees 1/2/6, explicitly, with the owner's sign-off) **before** proceeding to implement a weaker version — not implement first and document the weakening after the fact.

**Evidence-use instruction, recorded verbatim as directed**: M-L3's batch-size throughput curve is supporting evidence that batching *can* improve throughput; it is explicitly **not** treated as proof that any particular batched design will bring G6's persist share under 30%/50% — PERSIST-01's own acceptance condition (a built-and-measured re-run, RT-13/RT-14) remains the only thing that can establish that, unchanged from Phase 3/5.

**Problem statement.** Three distinct problems share one track because they all touch `contracts/local-job-engine.md` and its harness implementation: (1) a `symbols`-kind job, if redelivered after already completing, is not idempotent — the underlying Feature 002 `extractFile` path deletes and reinserts symbol rows with new ids, breaking any relationship row that pointed at the old ids (36 dangling endpoints observed at M-L4). ## K.2 — G6 persistence remediation (batching)

**Problem statement.** The engine commits one SQLite transaction per file per job kind (one `BEGIN IMMEDIATE…COMMIT` cycle per `symbols` unit's completion write, one per `contains` unit, one per `parsed` unit — see Research §2 below), so the *fixed* cost of acquiring the write lock and committing is paid once per file rather than being amortized across many files' rows in one transaction. At R-M's average of ~45 relationships/file, this fixed cost dominates: persist share is 62–68% of parsed-unit pipeline time across every tier measured (R-S 62.2%, R-M 64%, GitNexus 66.8%, iata-rl 67.6%), consistently exceeding the registered 30% [ENG] figure and the ">50% = overhead dominates" FAIL line.

**Evidence** (already captured):
- M-L5 `parsedPersistShare` field, all six tier files, c=2: 0.64 (R-M), 0.622 (R-S), 0.6683 (GitNexus), 0.6763 (iata-rl).
- M-L3 batch-size sweep (`m-l3-sqlite.json`, `t007-local-feasibility-results.md` §3): single-commit 48,370 rel/s vs. 1000-row-batch 42,254 rel/s vs. 100-row-batch 34,487 rel/s vs. per-row (batch=1) 10,708 rel/s (WAL) — throughput is highly sensitive to how many rows share one commit.

**Current contract/implementation** (read this pass, unmodified — `scripts/t007-local/lib/unit.ts`): `runParsed` (lines 293–454) wraps its **entire** persist step — DELETE-then-INSERT of that one file's relationship rows plus the job's COMPLETED write — in exactly one `tx()` call (line 415, `const wt = tx(ctx, () => {...})`), and `tx()` (lines 90–108) is exactly one `BEGIN IMMEDIATE…COMMIT` per call. `runContains` (line 228) and `runSymbols` (line 166, via `finish`→`completeJob`) follow the same one-transaction-per-unit pattern. `persistRows` (`lib/rel.ts:481`) itself contains no transaction management — it is a loop of prepared-statement `.run()` calls, and relies entirely on its caller's surrounding `tx()` for atomicity. **This confirms the root cause directly from source, not by inference**: the persist step is already correctly batched *within* one file's rows (a single transaction, per-row prepared statements — exactly the "single-commit" shape M-L3 measured at 48k rel/s), but the transaction boundary is drawn at the file level, not across files.

**Violated/unsatisfied gate condition.** G6's registered criterion: "SQLite persist ≤30% of pipeline wall… [ENG]." FAIL text: "overhead dominates (>50%)." 62–68% matches the FAIL text, not CONDITIONAL's "above, with a concrete batching/tuning proposal measured at least once" — no batching change has yet been built and measured against this actual bottleneck (M-L3's numbers are from a *different*, standalone bulk-insert benchmark, not this engine's own per-unit path).

**Existing relevant requirements.** Contract guarantee 1 (durability — "no job is lost or silently duplicated") and guarantee 2 (idempotency) both currently rely on the file-level transaction boundary: a file's relationship rows and its job-COMPLETED write land in the *same* transaction (line 430, `finish(ctx, job.id, checkpointOf(res.inserted))` called *inside* the `tx()` body), so a crash mid-transaction rolls back both together, and F-1's 56/56 clean kill/restart evidence is grounded in exactly this atomicity. **Any batching change that spans multiple files' persist work in one transaction must preserve this same atomicity property for every file in the batch, or F-1's durability evidence no longer applies to the new code path and must be re-verified.**

**Impacted documents.** F004 only — `contracts/local-job-engine.md` (if the contract's implicit "per-unit transaction" assumption needs stating explicitly, or amending, to describe a batched boundary instead) and the harness itself (`scripts/t007-local/lib/unit.ts`, `run.ts`, `worker.ts`/`engine.ts` — all PROTOTYPE, throwaway-but-promotable per plan §3, not production `src/`). No F001/F002/F003/F006/F009 document defines this transaction boundary; it is entirely local to F004's job-engine design.

**Dependencies.** None external — this is a self-contained F004 harness design change plus a re-measurement, once the SPECIFY questions below are answered.

**Risks.** Batching multiple files' persist work into one transaction extends the write-lock hold time per commit (fewer, larger transactions) — this could change the *concurrency-scaling* picture (M-L4's ladder, which already showed write-lock-wait rising 0%→72% with c=1→8) in a direction that needs re-checking, not assumed. It also changes the failure-injection blast radius: F-2 ("that unit FAILED/RETRYING; other files unaffected") currently relies on one file = one transaction = one failure domain; if N files share a transaction, an F-2-style single-file fault would need to either still isolate to one file (requiring per-file savepoints inside the batch) or the containment guarantee's scope needs to be explicitly redefined for the batched case.

**Ambiguity.** How many files' worth of work should share one transaction (a batch-size choice with its own throughput/latency/durability-blast-radius tradeoff, informed by but not identical to M-L3's row-count-based batch sweep, since this batch axis is *file count*, not *row count*, and files vary hugely in row-count-per-file across the four measured tiers).

**Questions requiring SPECIFY decisions:**
1. Batch by file count, by accumulated row count, by elapsed time, or some combination?
2. Does the job's COMPLETED write for every file in a batch still happen inside the same transaction as that file's rows (preserving today's atomicity per file), or does batching mean N files' rows commit together while their COMPLETED writes happen separately (weakening the current guarantee-1/2 coupling)?
3. Does a single-file fault inside a batch still contain to that file (F-2's guarantee), or does one bad file now roll back the whole batch (a containment-scope change requiring an explicit contract amendment, not a silent behavior change)?
4. What durability re-verification (a scoped F-1 re-run against the batched code path) is required before G6's remediation can be trusted the way today's per-unit-transaction G1/G2 evidence is trusted?

## K.2 research findings

- **Exact SQLite persistence path**: `lib/unit.ts` — `runSymbols` persists via F002's own D1-shim path (not the `tx()` helper directly; the D1 shim's own per-statement autocommit is a *separate*, F002-owned persistence mechanism, out of scope for a T007-side batching change unless F002 also changes). `runContains`/`runParsed` persist via the shared `tx()` helper (lines 90-108).
- **Transaction boundaries**: `tx()` wraps exactly one `BEGIN IMMEDIATE` / body / `COMMIT` per call; every one of `runContains`'s two call sites (line 238 for `*dirs`, line 271 for a single file) and `runParsed`'s one call site (line 415) invoke `tx()` exactly once per unit. **There is currently no code path that shares one transaction across multiple files' units.**
- **Batch sizes**: none — the current "batch" is always "one file's rows" (for `parsed`/`contains`) or "one file's symbol set" (for `symbols`, via the F002 D1 shim, whose own batching behavior is F002's concern).
- **WAL behavior**: `openDb` (`lib/db.ts`, not fully re-read this pass beyond what M-L3 already characterized) sets WAL + `synchronous=NORMAL`; M-L3's own characterization (§3 of the results doc) of WAL-vs-DELETE and batch-size sensitivity stands unchanged, read not re-measured.
- **Symbol/relationship/candidate writes**: `persistRows` (`lib/rel.ts:481-521+`) — one prepared `INSERT … ON CONFLICT (snapshot_id, relationship_key) DO NOTHING` per relationship row, one prepared `INSERT … ON CONFLICT DO NOTHING` per candidate row, both inside whatever transaction the caller already opened. **`persistRows` itself is already transaction-agnostic** — it does not call `BEGIN`/`COMMIT` — which means the batching change can be made **entirely in the caller** (`runParsed`/`runContains`, or a new coordinating function above them) **without modifying `persistRows`'s own signature or behavior.** This is a materially lower-risk finding than assuming the insert logic itself needs rework.
- **Indexes involved**: unchanged from M-L3's characterization (`idx_relationships_snapshot_source/target`, `idx_symbols_snapshot_name`) — batching transaction boundaries does not touch index structure.
- **Job bookkeeping writes**: `completeJob` (`jobs.ts:173-184`) is called *inside* the same `tx()` as the file's relationship rows (via `finish()`, `unit.ts:79-87`) for `contains`/`parsed`; for `symbols`, `finish()` is called in its *own* separate `tx()` (`unit.ts:199-207`) — i.e., **the `symbols`-kind job's completion write is already a *second*, smaller transaction distinct from its (F002-owned) persist step** — a detail the batching design for K.2 should account for, since `symbols` units already have a different transaction shape than `contains`/`parsed` units.
- **Origin of the 62–68% persist share, confirmed from source (not inferred)**: one `BEGIN IMMEDIATE…COMMIT` cycle is paid per file, for files that on average carry only ~45 relationship rows (R-M: 10,755 relationships ÷ 239 files) — well inside the range M-L3 already showed has poor throughput-per-commit (M-L3's 100-row-batch cells: 27–34k rel/s vs. its 1000-row-batch cells: 37–48k rel/s). **The persist-share finding and the M-L3 batch-size curve are talking about the same physical bottleneck (transaction-boundary fixed cost), confirmed by matching the engine's actual row-count-per-transaction (~45) against M-L3's own measured curve at that scale — not merely "suggestive," as L14 conservatively stated, but now directly traceable to a specific line of code (`unit.ts:415`).**
- **Batching without changing graph semantics**: confirmed feasible in principle — `persistRows`'s `ON CONFLICT … DO NOTHING` upsert semantics are idempotent regardless of how many files' rows are inserted in one call, and the DELETE-then-INSERT pattern (`unit.ts:416-420`) is scoped by `evidence_file_extraction_id`, so batching N files' DELETE+INSERT pairs into one transaction does not change which rows exist afterward — only *when* they become visible/durable (i.e., together, at the batch's commit, rather than one file at a time). The semantic risk is entirely in **failure containment and completion-write coupling** (Phase 1's risk/ambiguity items), not in the insert logic itself.
