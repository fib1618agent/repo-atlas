# Research: Settings / Control Plane

**Feature**: 006-settings-control-plane · **Date**: 2026-09-24 · **Spec**: [spec.md](./spec.md)

Phase 0. All findings are from the repository at the time of writing (labels: FACT = read from code/config; DECISION = plan decision). No Cloudflare access, no Wrangler, no GitNexus, no network was used. No `NEEDS CLARIFICATION` remains in the Technical Context; open plan-level items are in plan.md §Remaining Ambiguities.

## R1. Settings route and navigation

- FACT: every existing route is a file route with `ssr: false` (`src/routes/about.tsx` etc.). Each route renders its **own** header with a duplicated `<nav aria-label="Primary navigation">` (`index.tsx:177`, `catalogue.tsx:79`, `categories.tsx:107`, `insights.tsx:164`, `about.tsx:69`). There is no shared Navbar/Header component. The nav is `hidden … lg:flex` (not shown below the `lg` breakpoint) on all pages.
- FACT: `routeTree.gen.ts` is produced by the TanStack router plugin.
- **Decision**: add `src/routes/settings.tsx` and add one `Settings` link to each of the five existing headers; do not extract a shared nav component (would restructure five files beyond the requirement; Feature 003 made the same call). `routeTree.gen.ts` is regenerated by the plugin, never hand-edited.
- Alternative rejected: a shared `PrimaryNav` component. Larger diff, touches visual structure (SC-006).

## R2. Configuration read model and where effective values come from

- FACT: effective category-B values already exist as functions: `serverAtlasConfig()` (`atlas-config.ts`) and `codeIntelConfig()` (`code-intel/config.ts`). Both read `process.env` and use `Number(env ?? default)`.
- FACT: an invalid numeric override (for example `ATLAS_MAX_SOURCES=abc`) yields `NaN`; neither function falls back. `serverAtlasConfig()` parses `ATLAS_INITIAL_SOURCES` tolerantly (falls back to the default owner entry).
- **Decision**: the read model **calls these functions** for effective values (so it reports what the system actually uses, FR-013) and classifies a non-finite numeric result (`Number.isFinite`) as **Invalid / unavailable**, rather than re-reading `process.env` for those values. It does not change either function and does not supply a fallback (F001–F005 behavior unchanged). RESOLVED 2026-09-24 by user decision at plan review: spec FR-013, US1 scenarios 4–5, FR-008 and SC-004 now state this.
- **Decision**: the set of visible items is an explicit **allowlist registry** (R3). The read model never iterates `process.env`.

## R3. Category classification and redaction (allowlist, not denylist)

- **Decision**: one pure data module, `setting-registry.ts`, defines every item: `id`, label, category (A–D), default, validity rule, change mechanism, display form (`value` | `status` | `availability`), and `clientVisible`. Redaction is by **display form**, not by filtering values afterwards: a category-C entry's DTO type has no value field, a sensitive non-secret entry's DTO type has no value field, so a leak requires a type-breaking change and is caught by the SC-002 test.
- FACT (secrets present in code): `GITHUB_TOKEN` (`cloudflare-env.ts` `getGitHubToken()`), `GEMINI_API_KEY` (`ai/gemini.ts`), plus `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `XAI_API_KEY` declared in `.env.example` as stubs. → category C, status only.
- FACT (sensitive non-secret): `ATLAS_SQLITE_PATH` (local path), D1 `database_id`, bucket and queue names in `wrangler.toml`, `NITRO_PRESET`/`CF_PAGES` platform markers. → SEC-007 availability only. Binding presence uses existing `canUseD1()` / `canUseR2()` / `canUseSqlite()`; queue binding presence uses `getCloudflareEnv()` (no new binding access mechanism).
- **Decision**: `CODE_INTEL_RELATIONSHIP_*` tunables and `RELATIONSHIP_EXTRACTOR_VERSION` are **not** in the registry. They belong to Feature 004, which is not a dependency; the other `CODE_INTEL_*` tunables and `SYMBOL_EXTRACTOR_VERSION` are shown read-only, with no Cloudflare limit claim.

## R4. Client-visible environment variables (SEC-003, SEC-008)

- FACT: `.env.example` declares `VITE_SITE_URL`; no source file currently reads `import.meta.env.VITE_*` (grep of `src/` and `plugins/`), so it is declared but unused.
- **Decision**: registry marks `VITE_SITE_URL` as category B, `clientVisible: true`, display `value`, labeled "client-visible". Its value is read on the server from `process.env["VITE_SITE_URL"]` (the value is by definition non-secret). A drift test parses `.env.example` and fails if any `VITE_*` name is missing from the registry or is classed C, and if any category-C entry is marked client-visible.

## R5. Personal preference persistence (reuse decision)

- FACT: `sources-store.ts` uses zustand `persist` (name `repoatlas.sources.v1`, `partialize`, hydration flag). `atlas-store.ts` holds `autoRotate` and `showRelationships` but is **not** persisted, and also holds high-frequency transient state (`hoveredId`, `selectedId`).
- FACT: zustand `persist` serializes and writes storage on **every** `set`. `hoveredId` changes at pointer speed, so wrapping `atlas-store` in `persist` would write storage on every hover even with `partialize` (NFR-003, Constitution IV).
- **Decision**: keep `atlas-store` as the single runtime source of truth (existing consumers unchanged); add a small isomorphic `preferences.ts` (defaults, `sanitizePreferences`, guarded read/write, storage probe) and:
  - initialize the two fields in `atlas-store` from `readStoredPreferences()` (returns defaults when there is no `window`/storage or the data is malformed), and
  - add a `subscribe` listener that writes storage **only when one of the two preference fields changed**.
  Storage key `repoatlas.preferences.v1`, following the existing key convention. No new library.
- Rejected: (a) `persist` on `atlas-store` (per-hover writes); (b) a second preferences store with all consumers rewired (touches `AtlasScene`, `index`, `AtlasControls` for no gain); (c) any server-side or D1/SQLite storage (violates FR-011).
- Reset: `resetPreferences()` action sets both fields to defaults; the listener persists the defaults. It does not touch `sources-store` or the filters (FR-015; the Sources "Reset to default" stays in Feature 003).
- FR-010 (storage unavailable): zustand and the guarded writer never throw; a `probePreferenceStorage()` (try write/remove a test key inside try/catch) lets the Settings page state "will not be remembered".
- FR-007 note: the only editable controls are two booleans (switches), so free-form invalid input cannot be entered; validation applies to **stored** data via `sanitizePreferences` (per-item fallback to default, FR-009).

## R6. Server/client boundary and the server-function pattern

- FACT: server logic lives in `*.functions.ts` as an exported plain `…Handler` plus a thin `createServerFn` wrapper (`repositories.functions.ts`, `snapshot.functions.ts`), because `createServerFn` needs the Start request context and is not callable under `bun test`; tests call the handlers.
- FACT: React Query + `useServerFn` is the client access pattern (`use-atlas-repositories.ts`).
- FACT: functions not referenced by any UI need a registration component to stay reachable over `/_serverFn/<id>` (`feature-00x-server-fn-registration.tsx`). The Settings page references its own functions, so no registration entry is needed.
- **Decision**: new `src/lib/control-plane/control-plane.functions.ts` with the same handler/wrapper split; the two functions accept **no input** (validator returns `undefined`), so SEC-004 has no server-side user input to validate for this feature, and a test asserts the handlers ignore any supplied data.

## R7. Code-intelligence status read model (US3)

- FACT: existing F001/F002 status functions take a `snapshotId` (`getSnapshotStatus`, `getExtractionStatus`); nothing enumerates snapshots. Statuses: `snapshots.status` ∈ {pending, in_progress, completed, failed}; `snapshot_extractions.status` ∈ {in_progress, completed, completed_partial, failed} (`data/code-intel-schema.sql`).
- FACT: D1 is available only when `globalThis.__env__` carries `DB` (`cloudflare-env.ts`: `canUseD1()`); under plain `vite dev` it is absent.
- **Decision**: a new read-only module `code-intel-status.ts` runs two aggregate `SELECT status, COUNT(*) … GROUP BY status` queries against `snapshots` and `snapshot_extractions` via the existing `getD1()`/`canUseD1()` helpers, and reads `SYMBOL_EXTRACTOR_VERSION` from `config.ts`. No F001/F002 file is modified. It returns counts only (no repository owners/names, no identifiers). If D1 is unavailable it returns `available: false` with a fixed reason code (FR-018). It never issues INSERT/UPDATE/DELETE and never enqueues.
- Rejected: per-snapshot listing (needs a new pagination contract and exposes repository identifiers; not required by FR-014/US3), calling the existing per-snapshot functions in a loop.

## R8. Network-reachable safety (SEC-005, no authentication)

- FACT: there is no authentication anywhere; the existing F001/F002 server functions are already reachable to whoever can reach the instance.
- **Decision**: safety is **content-based**. The DTO is built from the allowlist, the DTO types for C and sensitive items carry no value field, error responses use fixed catalog text (never `Error.message`, never stack traces), and nothing from `process.env` or `wrangler.toml` is passed through unfiltered. A test sets sentinel values for every secret and sensitive item and asserts none appears in the serialized DTOs or error output (SC-002, SEC-001/006/007). No auth/RBAC architecture is introduced.

## R9. Errors and empty/loading/unavailable states

- FACT: `atlas-errors.ts` holds the documented catalog (`AtlasErrorCode` + `ERROR_MESSAGES`, with recovery actions Retry / Reset to default / Dismiss in the UI); `ui/alert`, `ui/skeleton`, `sonner` exist.
- **Decision**: add exactly one catalog code, `SETTINGS_UNAVAILABLE` (fixed message, no interpolation of internals), for a failed configuration read; the page shows an Alert with **Retry**. States: loading (Skeleton), error (Alert + Retry), unavailable capability (badge "Unavailable" + fixed reason text, not styled as failure, FR-018), empty code-intel data ("No code-intelligence data").

## R10. UI composition

- FACT: the shadcn kit already has `card`, `switch`, `badge`, `alert`, `skeleton`, `button`, `separator`, `table`, `tooltip`. `about.tsx` holds page-local building blocks (not exported) using atlas classes (`atlas-page`, `atlas-header`, `atlas-eyebrow`).
- **Decision**: Settings page composes existing UI primitives and atlas classes; nothing is extracted from `about.tsx`. No new dependency (Constitution V).

## R11. Testing

- FACT: runner is `bun test --isolate`; tests live in `tests/{unit,contract,integration,support}`; `tests/support/d1-sqlite-adapter.ts` provides an in-memory `D1DatabaseLike` loaded with `data/code-intel-schema.sql`; `setTestCloudflareEnv` injects bindings; `tests/unit/atlas-config.test.ts` shows the env save/restore pattern. There is no browser/component test tooling (no testing-library, jsdom, or Playwright in `package.json`).
- **Decision**: unit and integration tests only for logic (registry, read model, redaction, preferences sanitizer/reset, code-intel status with the in-memory D1). UI behavior is verified by typecheck plus the manual steps in quickstart.md; no new test framework is added.

## R12. Local validation

- FACT: `bunx tsc --noEmit` must pass (constitution); `bun test`; dev server via `./run.sh` (port from 4949). Under plain dev, D1 is absent, so US3 shows the unavailable state locally; its data path is proven by the integration test with the in-memory adapter (SC-005 requires only US1/US2 to run with no platform account).
