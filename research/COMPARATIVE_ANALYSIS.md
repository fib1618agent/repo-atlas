## Cross-cutting observations

[RESOLVED] Both reference projects assume a **local filesystem checkout** as the ingestion starting point. RepoAtlas's GitHub-API-first model is architecturally distinct from both — this is neither a gap nor a strength per se, but it means the ingestion layer cannot be adapted from either reference; it must be designed to bridge "hosted API metadata" and "local-checkout-style AST analysis," likely via an explicit clone/checkout or content-fetch step (see `SOURCE_PROVIDER_ANALYSIS.md` §4).

[RESOLVED] Both references reject vector/embedding search in favor of graph-structural + lexical signals. This is a **consistent, deliberate** choice in both codebases (not an oversight), and is relevant evidence against defaulting to a vector-DB-based design for RepoAtlas's own retrieval architecture (see `KNOWLEDGE_RETRIEVAL` evaluation in `REPOATLAS_EVOLUTION.md` §11).

[RESOLVED] Neither reference solves commit-SHA-addressable source snapshots — this is the one clearly novel piece of infrastructure RepoAtlas would need to build with no direct architectural precedent from either reference (though CodeGraph's `indexed_at_commit` + git-diff fast path is a reusable _concept_ for change detection, not snapshot storage).

[INFERRED] The single largest constraint differentiating RepoAtlas from both references is the **Cloudflare Workers production runtime** — neither Graphify (Python, unconstrained local execution) nor CodeGraph (Node CLI/daemon, unconstrained local execution) operates under per-request CPU-time limits or lacks-filesystem-access. Any capability adapted from either reference needs a redesign pass specifically for this constraint before being considered portable.
