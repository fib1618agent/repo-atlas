## 2. Evidence model (EXTRACTED / RESOLVED / INFERRED / UNKNOWN)

[RESOLVED] Comparing to Graphify's evidenced 3-state model (EXTRACTED / INFERRED / AMBIGUOUS) — the proposed 4-state RepoAtlas model splits Graphify's implicit "deterministically resolved from indirect evidence" cases into two states (RESOLVED vs INFERRED), which Graphify does not do explicitly (Graphify's EXTRACTED covers both "directly observed" and, in practice, some deterministic cross-file resolution results — e.g. an import resolved to a concrete file is still tagged the same confidence tier as extraction unless it becomes ambiguous).

CodeGraph's model is coarser still: a binary `provenance: 'tree-sitter' | 'heuristic'` tag, with no numeric confidence and no distinct "deterministically resolved" tier.

**Verdict**: the proposed EXTRACTED/RESOLVED/INFERRED/UNKNOWN four-state model is **more precise than either reference's actual implementation**, not less. This is not evidence it's wrong — it is evidence it's untested at this precision level. [INFERRED] The extra RESOLVED tier (deterministic resolution from symbols/imports/exports/scopes/types) is a reasonable and useful distinction that neither reference bothered to make explicit, likely because neither needed the finer grain for their retrieval/ranking use cases. RepoAtlas's Impact Analysis use case (§13 below) plausibly benefits from distinguishing "the import statement literally says X" (EXTRACTED) from "we resolved that import to file Y via module resolution rules" (RESOLVED) from "we think this call targets method Z because of a naming convention" (INFERRED), since impact-analysis confidence should degrade differently across these.

**Is UNKNOWN sufficient, or are more states needed?** [INFERRED] Graphify's AMBIGUOUS (flagged for human review, distinct from "unresolved") is not directly represented in the proposed 4-state model — UNKNOWN conflates "we haven't tried to resolve this" with "we tried and got multiple candidates with no way to disambiguate." Recommend considering whether AMBIGUOUS (or an AMBIGUOUS sub-flag on UNKNOWN) should be added before implementation — this is exactly the kind of edge case Graphify's test suite (`test_inferred_confidence_rubric.py`) exists to prevent regressing on.

**Verdict**: the 4-state model is sufficient as a starting taxonomy, with one open question (should AMBIGUOUS be distinguished from UNKNOWN) flagged for the foundation-phase spec, not resolved here.

## 3. Source snapshot model

Proposed: `Provider → Repository → Commit/Snapshot → File Index → AST → Symbols → Relationships → Engineering Graph`, with the commit-SHA snapshot as the authoritative evidence layer and SQLite/DB as structural/query representation only.

[RESOLVED — see `SOURCE_PROVIDER_ANALYSIS.md` for full detail] Neither reference implements this pipeline in full. CodeGraph's `indexed_at_commit` is the closest partial precedent, but it's a single mutable pointer for change-detection, not a queryable snapshot history. The "database is not the source of truth, the snapshot is" principle is **not evidenced by either reference** (both treat their DB/graph.json as the operative artifact, with no separate concept of "the authoritative commit-pinned source" distinct from what's indexed) — but it is also not contradicted; it's simply a stronger authority-tracking discipline than either reference bothered to implement, likely because neither operates in a multi-tenant, re-verifiable, edge-deployed context where "can we prove this graph reflects exactly commit X" matters as much as it would for RepoAtlas.

**How the existing GitHub implementation could support this pipeline** [INFERRED, building on `SOURCE_PROVIDER_ANALYSIS.md`]:

- `Provider`: new abstraction, not yet existing (§`SOURCE_PROVIDER_ANALYSIS.md` §1).
- `Repository`: existing `repositories` table extends naturally (`source_key` already ties a repo to its provider-source).
- `Commit/Snapshot`: new table needed — repo + commit SHA + fetch metadata. Does not exist today.
- `File Index`: new table needed — path/blob-hash/language per snapshot. Does not exist today.
- `AST`/`Symbols`/`Relationships`: new tables/storage, informed by CodeGraph's `nodes`/`edges`/`unresolved_refs` schema shape (ADAPT, not copy) but must be designed for Workers-compatible storage (D1 or equivalent, not `node:sqlite`).
- `Engineering Graph`: the query-time composition of the above — this is the layer both references' `build.py`/`GraphTraverser` operate at, and is the best-evidenced part of the whole pipeline.

## 5. Process discovery

Proposed: `Entry Points → Routes/handlers → Calls → Services → Repositories/data access → External boundaries → Side effects`, evaluated as a possible first-class graph capability.

[RESOLVED, from `ENGINEERING_LINEAGE.md`] Confirmed absent from both references as a first-class capability. The building blocks exist (route/component nodes in CodeGraph via framework resolvers; call-graph traversal in both), but no reference reconstructs an end-to-end process chain from entry point through side effects.

**Should it be first-class?** [INFERRED] The individual edges needed (CALLS, ROUTES, READS/WRITES for data access, external-boundary detection) are either evidenced (CALLS) or explicitly flagged above as DEFER/UNRESOLVED (ROUTES needs framework resolvers; READS/WRITES have no precedent at all). Making Process a first-class _node_ type is premature per §1 above. Making process _discovery_ a query-time derived capability (a labeled path through the existing CALLS/ROUTES graph, computed on demand, similar to CodeGraph's `named-symbol-flow.ts` — which finds a call-path connecting named symbols, the closest existing precedent to "process discovery" found in either reference) is better supported by evidence than persisting Process as a stored node/subgraph.

**Verdict**: process discovery is a plausible and valuable capability, but should be scoped as a **derived query-time traversal** (informed by CodeGraph's `named-symbol-flow.ts` pattern — ADAPT) rather than a first-class persisted graph concept, until framework resolvers and READS/WRITES edges exist to make "external boundary" and "side effect" detection meaningful.

## 6. Impact analysis

Proposed: `NL/identifier → Target Lock → Node → Backward traversal → CALLS/IMPORTS/REFERENCES → Entry Bounds → Affected processes → Impact report`.

[RESOLVED] Directly and strongly evidenced by Graphify's `affected.py` — a near 1:1 match: fuzzy seed resolution (`resolve_seed`, analogous to "Target Lock"), reverse BFS over a filterable relation set (`affected_nodes`), depth bounding, and a formatted report with actual call-site locations (`format_affected`). CodeGraph's `getImpactRadius` is a simpler BFS-based analog.

**"Affected processes" step**: [UNKNOWN] this step assumes Process Discovery (§5) exists as a prerequisite — since Process Discovery is evidenced as a _derived_ capability rather than a persisted graph layer (§5's verdict), "Entry Bounds → Affected processes" should be understood as "traversal stops at recognized entry-point nodes, and the _report_ groups affected nodes by the process/entry-point they belong to" — a presentation/grouping concern layered on top of the same reverse-BFS Graphify already implements, not a separate prerequisite phase. This resolves the sequencing tension flagged in `ENGINEERING_LINEAGE.md`.

**Distinguishing structurally-proven vs inferred vs unresolved impact** [RESOLVED, directly evidenced]: this is exactly what Graphify's confidence-tagged relation set does — `DEFAULT_AFFECTED_RELATIONS` includes both EXTRACTED-tier relations (`calls`, `imports`) and edges that may carry INFERRED confidence (`dynamic_import`, `indirect_call`). A well-designed impact report should surface this distinction per-hit, matching Graphify's `AffectedHit` shape (which includes `via_relation`, letting the report show _how_ each affected node was reached). **"Blast radius" should not be presented as uniformly exact — both the confidence-rubric evidence (§2) and Graphify's own relation-tagging practice support qualifying each hit by the evidence tier of the edges it traversed through.**

**Verdict**: impact analysis is the best-evidenced of all the proposed new capabilities — Graphify's `affected.py` is close to a direct architectural template (ADAPT, not copy — see `ADOPTION_MATRIX.md` item 8).

## 7. Lazy context hydration

Proposed: `Graph first → Find relevant nodes → Rank evidence → Select bounded context → Hydrate source snippets only when required`.

[RESOLVED] Strongly evidenced by both references' MCP layers: Graphify's token-budgeted responses (`_cut_lines_to_budget`, default 2,000 tokens) and CodeGraph's adaptive per-repo-size budget (`getExploreBudget`/`getExploreOutputBudget`) both implement exactly this principle — query the graph, rank/select, then bound the output rather than dumping raw source. CodeGraph's design is more mature (tiered by repo size, with pinned-file guarantees and tested invariants).

**Does this fit RepoAtlas?** [INFERRED] Yes, and more urgently than for either reference: RepoAtlas's production Workers runtime has hard CPU-time and response-size constraints (`REPOATLAS_CURRENT_ARCHITECTURE.md` §12) that make "never load a whole repo into context" not just a good practice (as it is for the references, which run as local CLI tools with no such constraint) but closer to a **hard requirement** for RepoAtlas's MCP/agent interface to function within its production runtime at all.

**Verdict**: strongly evidenced, and higher-priority for RepoAtlas than for either reference given the edge-runtime constraint.

- `06-process-discovery` before `07-impact-analysis`: [RESOLVED, revised by this analysis] Per §5-6 above, this strict ordering is **not required by evidence** — Impact Analysis (well-evidenced, Graphify-precedented) does not need Process Discovery (unevidenced, higher-risk) as a hard prerequisite; it needs the Engineering Graph and Knowledge Retrieval layers. **Recommend evaluating whether these two phases should be reordered (Impact Analysis before Process Discovery) or merged/run in parallel**, since Impact Analysis is lower-risk, has a near-direct architectural template (`affected.py`), and delivers value sooner, while Process Discovery is higher-risk and better validated after the team has direct experience with the graph from building Impact Analysis first.

- `10-integration-hardening`: [INFERRED] reasonable as a final phase; standard practice, not something either reference specifically evidences as a discrete phase (both treat hardening as continuous, not a phase-gated step) — but not contradicted either.

**Coupling/splitting candidates**:

- [INFERRED] `03-ast-symbols` (polyglot AST & symbol resolution) is, per both references, actually two somewhat separable concerns: raw per-language extraction (evidenced as highly pluggable/declarative in Graphify) vs. cross-file symbol _resolution_ (evidenced as a distinct pass in both references — Graphify's `resolver_registry.py`, CodeGraph's `ReferenceResolver`). Consider whether this phase is large enough to warrant splitting into "AST extraction" and "Symbol resolution" as the corpus grows past initial languages — not urgent for Phase 1, worth flagging for the phase's own planning.
- [INFERRED] `06-process-discovery` and `07-impact-analysis` are candidates for reordering or merging, per the analysis above — not because they're wrongly _coupled_, but because their evidenced dependency direction may be backwards from what's currently specified.
